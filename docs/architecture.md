# Architecture

## Общая схема

Проект использует простой слоистый подход. Telegram-обработчики принимают сообщения, выбирают активную модель и вызывают клиент нужного провайдера. Клиенты провайдеров инкапсулируют HTTP-запросы к внешним API. Точка входа собирает приложение и запускает polling.

## Структура каталогов

```text
bot/
├── config.py            # Загрузка и хранение настроек
├── handlers/
│   └── main.py          # Команды Telegram и чат-сообщения
├── llm_clients/
│   ├── base.py          # Общий интерфейс ask()
│   ├── gigachat.py      # Клиент GigaChat
│   └── yandex.py        # Клиент YandexGPT
├── main.py              # Валидация конфигурации и запуск бота
└── system_prompt.py     # Общий system prompt
```

## Поток запроса

1. Пользователь отправляет команду или обычное сообщение в Telegram.
2. `bot/handlers/main.py` определяет команду или текстовый запрос.
3. Для текстового сообщения хендлер выбирает модель пользователя или fallback из `LLM_DEFAULT`.
4. Выбранный клиент из `bot/llm_clients/` отправляет HTTP-запрос к GigaChat или YandexGPT.
5. Ответ возвращается в Telegram как обычное сообщение.

## Границы модулей

- `handlers` знают о Telegram и о реестре клиентов.
- `llm_clients` знают о внешних API и конфигурации, но не должны зависеть от Telegram.
- `config.py` должен оставаться простым слоем загрузки env-переменных.
- `main.py` выступает composition root и не должен содержать бизнес-логику общения с провайдерами.

## Ограничения текущей реализации

- Выбор модели хранится в памяти процесса и теряется после рестарта.
- База данных и постоянное хранилище отсутствуют.
- Автотесты пока не добавлены.
- Проверка реальных интеграций зависит от рабочих ключей в `.env`.

## Когда усложнять архитектуру

Имеет смысл вводить дополнительные слои только если появятся:

- несколько типов обработчиков и сложные сценарии маршрутизации
- хранение пользовательских настроек в БД
- отдельные сервисы для rate limit, логирования или retries
- тестовая инфраструктура с mock-клиентами и фикстурами
